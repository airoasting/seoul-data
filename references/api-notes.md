# 서울 열린데이터광장 Open API 실측 노트

2026-11-14에 샘플 키와 실제 일반 인증키로 직접 불러 확인한 사실이다. 공식 문서에 없거나 문서와 다른 동작을 모았다. 각 항목 아래의 명령으로 다시 확인할 수 있다. 코드가 이 사실에 기대는 곳은 `assets/seoul_client.py`와 `assets/catalog.py`다.

## 1. 호출 규칙

```
http://openapi.seoul.go.kr:8088/{KEY}/{TYPE}/{SERVICE}/{START}/{END}/{인자1}/{인자2}/...
```

| 사실 | 확인 명령 | 코드의 대응 |
|---|---|---|
| 인자는 경로의 위치로 넘긴다 | 모든 서비스 공통 | `catalog.order_params` |
| 건너뛸 선택 인자는 공백(`%20`)으로 채운다 | `curl "…/sample/json/tbLnOpendataRtmsV/1/3/2026/%20/강남구"` | `seoul_client._seg` |
| 한 번에 최대 1,000행 (ERROR-336) | 명세 화면의 메시지 표 | `Client.rows`가 나눠 받는다 |
| 샘플 키는 1~5행만 (ERROR-335) | `curl "…/sample/json/bikeList/1/10/"` | 체험 모드로 5행까지만 |
| HTTPS가 안 된다 | `curl "https://openapi.seoul.go.kr:8088/…"` → exit 35 | 평문 HTTP. 오류 문장에서 키를 가린다 |
| 오류여도 HTTP 상태는 200 | `curl -o /dev/null -w "%{http_code}" "…/잘못된키/json/bikeList/1/1/"` | 본문의 CODE로 판정 |
| JSON을 요청해도 INFO-100, ERROR-335는 XML로 온다 | 위 두 명령 | `parse`가 XML 조각도 읽는다 |
| 없는 서비스명은 ERROR-310이 아니라 ERROR-500 | `curl "…/sample/json/NoSuchService/1/2/"` | ERROR-500 안내에 "서비스명 확인"을 넣는다 |
| 최상위 키가 서비스명과 다를 수 있다 | `bikeList` 응답의 키는 `rentBikeStatus` | `row`를 가진 첫 객체를 찾는다 |
| `list_total_count`가 전체가 아닐 수 있다 | `bikeList/1/3`의 값은 3 | 총계가 받은 행 수보다 클 때만 믿는다 |
| 필터 값의 `/`는 `%2F`로 넣어도 경로 구분으로 풀린다 | `culturalEventInfo/1/5/전시%2F미술` | 호출 전에 거절한다 |
| 그 결과가 오류 없이 다른 조건의 정상 응답으로 온다 | 위 명령은 CODENAME=전시, TITLE=미술로 풀려 334건을 준다 (CODENAME=전시만 주면 3,359건) | 받은 행 전체로 필터 반영을 확인한다 |
| 일부 필터는 앞부분 일치로 동작한다 | `culturalEventInfo/1/1/전시`가 `전시/미술` 3,359건을 준다 | 오류 안내에 '/' 앞부분만 넣어 보라고 적는다 |
| 응답 속도 0.02~0.44초 | 데이터 호출 0.10~0.44초, 오류와 작은 응답 0.02~0.05초. 1,000행 한 장은 0.34초(실제 키) | 도구당 기한 20초 |

### 장마다 행 순서가 바뀐다 (가장 조심할 것)

1,000행이 넘는 데이터를 여러 장으로 받을 때, 서울시 서버가 장마다 행 순서를 다르게 돌려주는 데이터셋이 있다. 정렬 기준이 고정돼 있지 않은 것으로 보인다.

| 확인한 것 (2026-11-14, 실제 키) | 값 |
|---|---|
| 종로구 일반음식점(`LOCALDATA_072404_JN`, 20,613행)을 한 번 통째로 받았을 때 서로 다른 관리번호 | 16,833개와 17,363개 (두 번 측정). 약 3,300~3,800행이 겹치고 그만큼 빠진다 |
| 같은 구간(1~1,000)을 연달아 두 번 불렀을 때 같은 행 | 1,000행 중 926행 |
| 같은 관리번호의 행 내용이 호출마다 달라지는가 | 아니다. 내용은 같고 위치만 바뀐다 |
| 부동산 실거래(`tbLnOpendataRtmsV`, 마포구 2026년 3,831행) | 한 번에 6~9행이 겹친다. 세 번 받으면 전부 맞춰진다 |
| 한 장 안에서 내용이 완전히 같은 행 | 마포구 실거래에 21건. 누락이 아니라 원래 두 번 기록된 거래다 |

코드의 대응(`Client._stable_rows`). 한 장 안에서 같은 행이 나온 횟수를 그 행의 실제 개수로 삼고(한 장은 한 시점의 일관된 결과다), 장 사이에서 다시 나온 행은 겹침으로 본다. 겹침이 보이면 시간이 되는 만큼 다시 받아 모은 행 수가 총계와 같아질 때까지 맞춘다. 못 맞추면 `rows_missing`과 함께 어림값이라고 알린다. `offset`으로 직접 넘겨 가며 세면 이 문제를 그대로 맞는다.

이 대응이 못 잡는 것.

- 조각으로 나눠 이어 훑을 때(`scan_offset`) 조각 사이의 겹침. 그래서 조각을 더한 값은 어림값이라고 알린다.
- 받는 사이에 값이 바뀌는 데이터. 같은 행이 다른 내용으로 보여 겹침으로 잡히지 않는다. 모은 행이 총계보다 많아지면 그 사실을 알리지만, 넘지 않으면 알 수 없다. 따릉이는 대여소 번호로 구분해 이 문제를 피한다.
- 순서가 고정된 서버에서 내용이 같은 두 행이 장 경계에 걸친 경우는, 한 번 더 받아 순서가 같으면 정상 행으로 본다.

다시 받는 횟수는 최대 5번이고(`Client.STABLE_PASSES`), 맞춰진 결과는 60초 캐시한다.

재현: 같은 집계를 `scan`을 주고 여러 번 불러 `meta.scanned`와 notices를 본다.

```
python3 assets/mcp_server.py --call dataset_query '{"dataset": "OA-18652", "group_by": ["TRDSTATENM"], "scan": 30000}'
```

## 3. 모양이 다른 API

### 실시간 도시데이터 `citydata` (OA-21285)

- 장소 121곳. 장소명이나 코드(`POI009`)로 부른다.
- 응답 봉투가 `{"list_total_count", "RESULT": {"RESULT.CODE", "RESULT.MESSAGE"}, "CITYDATA": {…}}`다. 결과 코드의 키에 `RESULT.`이 붙는다.
- 한 장소의 응답이 6만~16만 자다(장소와 시각에 따라 다르다. 광화문·덕수궁 14만~16만 자, 성수카페거리 약 6만 8천 자). 광화문·덕수궁 기준 도로 구간이 약 7만 9천 자, 전기차 충전소가 3만 7천~5만 자를 차지한다.
- 인구 값의 기준 시각(`PPLTN_TIME`)은 5분 간격으로 바뀌고, 조회 시각보다 20~30분 늦는 것을 여러 번 관찰했다.
- 실제 키로 121곳을 장소명으로 불러 모두 같은 이름이 돌아오는 것을 확인했다.
- `citydata_ppltn`은 인구만 준다(약 1,900자). 봉투가 `{"SeoulRtd.citydata_ppltn": [ … ]}`로 `row`도 `RESULT`도 없다.
- **샘플 키는 어떤 장소를 넣어도 `광화문·덕수궁`을 준다.** 장소별 동작은 실제 키로만 확인할 수 있다.
- 명세 화면은 TYPE을 xml만 적지만 json도 된다. 장소 수를 120곳이라 적은 곳도 있다.
- **명세가 틀린 필드.** `CUR_PRK_CNT`의 설명은 "주차장 주차 가능 면수"지만 실제 값은 주차된 차량 수다. 세종로 공영주차장이 같은 시각(21:50:43)에 `citydata`의 `CUR_PRK_CNT` 337, 시영주차장 데이터(OA-21709)의 `NOW_PRK_VHCL_CNT`(현재 주차 차량수) 337로 같았다.
- `citydata_eng`, `citydata_ppltn_eng` 같은 영문판 서비스도 있다. 샘플 키에서 같은 동작(광화문만)을 한다.

### 실시간 지하철 `realtimeStationArrival` (OA-12764)

- 호스트가 다르다. `http://swopenapi.seoul.go.kr/api/subway/{KEY}/json/realtimeStationArrival/0/5/서울`
- 인증키를 따로 신청한다. 하루 1,000건. 일반 인증키로 부르면 `ERROR-338`이 온다.
- 시작 위치가 0부터다.
- 정상 응답은 `{"errorMessage": {"status", "code", "message", "total"}, "realtimeArrivalList": [ … ]}`, 오류 응답은 `{"status": 500, "code": "ERROR-336", …}`로 모양이 다르다.
- 역 이름은 API마다 표기가 다르다. 실시간 API가 쓰는 이름 561개를 `assets/stations.py`에 모아 두었다(전체 도착 서비스 `realtimeStationArrival/ALL`을 한 번 불러 모았다. 이 서비스는 범위와 상관없이 2,952행을 한꺼번에 준다).
- 샘플 키는 `0/5/서울`만 된다. `0/2`나 다른 역(이름이 맞는 `강남`도)은 ERROR-336이다. 그래서 ERROR-336은 역 이름 오류의 증거가 아니다.
- 실제 지하철 키로 확인한 것 (2026-11-15).
  - 역 이름이 틀리면 오류가 아니라 `INFO-200`(데이터 없음)이 온다. `없는역이름`, `홍대`, `이수` 모두 그렇다. 그래서 빈 결과에는 역 이름을 확인하라는 안내를 붙인다.
  - **서울역은 이름이 둘로 나뉘어 있다.** `서울`에는 1호선, 4호선, 경의중앙선, 공항철도가, `서울역`에는 GTX-A만 온다. 한쪽이 다른 쪽의 일부가 아니다. 그래서 서울역은 두 이름을 모두 불러 합친다. 이런 역은 서울역 하나뿐이었다.
  - **괄호가 붙은 이름이 24곳 있다.** `천호`는 빈 결과이고 `천호(풍납토성)`으로 불러야 한다(군자(능동), 몽촌토성(평화의문), 오목교(목동운동장앞) 등). 괄호 앞부분으로도 찾게 했다.
  - 서울시 역 목록(`SearchSTNBySubwayLineInfo`)의 표기는 실시간 API와 다르다. 역 목록에는 1·4호선이 `서울역`, GTX-A가 `서울`로 거꾸로 적혀 있고, 괄호 이름이 없다.
  - **정렬.** `ordkey`(예: `11001서동탄0`)의 첫 글자는 상하행, 둘째는 순번, 셋째~다섯째는 몇 정거장 전인지다. 이 값으로 정렬해야 이 역에 들어오는 열차(0정거장, `barvlDt`는 0)가 맨 앞에 온다. `barvlDt`로 정렬하면 0인 행이 뒤로 밀린다.
  - **갱신 시각.** 신분당선은 `recptnDt`가 실제보다 4~5분 앞서 찍혀 올 때가 있다. 기준 시각은 지금을 넘지 않게 자른다. 종착역에서 대기하는 열차는 몇 분째 갱신되지 않는다. 지우지 않고 `stale`로 표시한다.
  - **범위.** `/0/N`과 `/1/N`은 같은 1~N행을 준다.
  - 호선 코드 19종(1001~1009, 1032, 1063, 1065, 1067, 1075, 1077, 1081, 1092, 1093, 1094)이 실제 응답에 나왔고 모두 코드표에 있다.
  - `총신대입구(이수)`는 괄호까지 넣어야 한다. `홍대입구`는 되고 `홍대`는 빈 결과다.
  - 한 번 호출에 0.04초. 강남 2호선은 `2분 20초 후`처럼 남은 시간(`barvlDt` 140초)이 실린다.
- 한 응답 안에 갱신 시각(`recptnDt`)이 몇 분씩 다른 행이 섞인다.

### 따릉이 `bikeList` (OA-15493)

- 대여소가 2,739곳이라 세 장으로 받아야 한다 (실제 키, 0.53초).
- `list_total_count`가 전체가 아니라 이번 장의 행 수다. 받은 행이 요청보다 적을 때까지 받아야 끝을 안다.

## 4. 카탈로그와 명세

| 필요한 것 | 길 |
|---|---|
| 데이터셋 검색 | `POST https://data.seoul.go.kr/dataList/datasetList.do`, 폼 필드 `basickwd`(검색어), `pageIndex`(쪽). 한 쪽 10건. 키가 필요 없다 |
| 서비스명, 인자 순서, 출력 필드 | `GET https://data.seoul.go.kr/dataList/openApiView.do?infId=OA-…&srvType=A&serviceKind=1`. 표 세 개(샘플 URL, 요청인자, 출력값) |
| 전체 목록 (공식 API) | `SearchCatalogService`. 8,316건. 키워드 필터와 서비스명 필드가 없어 쓰지 않는다 |

- 검색 결과에서 공공데이터는 `<dl class="type-b">`, 통계는 `<dl class="type-a">` 안에 있다.
- 통계 데이터셋은 ID가 `DT…`이고 SHEET와 CHART만 있다. 명세 화면이 404다.
- 자치구 데이터셋(예: `JungnangHealthRecruitList`)도 같은 호스트로 호출된다.
- 요청인자 표의 앞 다섯 행(KEY, TYPE, SERVICE, START_INDEX, END_INDEX)은 고정이다. 여섯째 행부터가 경로 인자이고 표의 순서가 곧 경로의 순서다.

### 문화행사 `culturalEventInfo` (OA-15486)

- 인자 순서는 CODENAME, TITLE, DATE다. CODENAME은 앞부분 일치(`전시` → `전시/미술`), TITLE은 부분 일치다.
- DATE는 그날 열리는 행사가 아니라 **종료일이 그날인 행사**를 준다. `DATE=2026-11-15`의 결과는 모두 `END_DATE`가 11-15였고 `STRTDATE`는 11-07부터 11-15까지 섞여 있었다. 진행 중인 행사를 찾으려면 `STRTDATE`와 `END_DATE`를 직접 견줘야 한다.

## 5. 값의 모양

- 숫자가 문자열로 온다(`"THING_AMT": "27500"`). 일부는 숫자형이다(`"ARCH_AREA": 32.63`). 이 서버는 바꾸지 않는다. 지번 `"0016"` 같은 값이 망가지기 때문이다.
- 단위는 값이 아니라 명세의 설명에 있다(`물건금액(만원)`). 그래서 응답에 `fields`를 붙인다.
- 날짜 형식이 세 가지다. `20261110`, `202611142000`, `2026-11-14 20:30`.
- 인허가 데이터(LOCALDATA_…)는 값 뒤에 공백이 붙어 오고, 좌표 X·Y가 위경도가 아니라 중부원점 TM이다.
- 구청 공고류는 한 셀이 수 KB다. 이 서버는 셀을 500자에서 자른다.
